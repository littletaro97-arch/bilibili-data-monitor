# 0.75秒共享限速、长连接与可选双账号接管

基线dacdce0，功能分支codex/pooled-dual-account-resilience。按用户要求并入Windows主程序源码，保持版本号0.14.0不变，不打包、不推送、不发布Release。

## 最终行为

业务API共享0.75秒起始间隔、一个串行请求通道，避免叠加“响应结束再等3秒”。公开请求、主账号、备用账号各有独立长期HTTP连接池，按需创建；SSLContext共享一次创建，认证Cookie按账号隔离且每次使用显式凭据，公开请求不携带账号Cookie。扫码passport会话同样复用这个SSLContext，但保留原扫码轮询间隔和各账号独立会话。程序退出关闭全部池。
主账号沿用原auth/bilibili-auth.dat，备用使用独立bilibili-backup-auth.dat，Windows用户加密。任意一个登录位置有效即可抓取；第二账号推荐但非必需，同一账号不能重复填入两个位置。未登录视频公开统计仍按原方案运行，正文等待登录。
两个账号都可用时，新自动正文任务按视频稳定分配，UP按目标分配；已有正文任务不随账号恢复抢回，以免反复移交。一个账号退出/明确失效，另一个接续原任务ID、pending楼中楼索引/页码、评论offset、分P和segment。创建账号作为历史保留，接管版本递增，旧执行者提交被拒绝。正文仍采用原单执行者调度，不让两个账号并行采同一任务。
HTTP401若不是明确code=-101，会先验证账号；账号仍有效但内容访问拒绝时不把账号判过期、不换号。网络超时继续按原递增重试，平台限流保持全通道共享冷却，不用备用账号绕过限制。手动暂停/回收站任务不自动接管。
跨账号旧评论游标返回明确参数错误时，只在接管初次、无未处理pending根评论且有旧offset的情况下允许一次从首页去重续查，保留原文和已完成根列表。采用新的游标扫描周期避免旧游标哈希误报循环。再次失败暂停，不无限重扫。不同账号可见性可能不同，UI明确“当前采集账号不可见”，不直接判定全平台删除。
登录后只恢复因登录失效等待的UP任务，不恢复用户暂停的任务，也不清除原风险冷却。手动更换同一账号位置为另一个账户时，自动任务先暂停；用户主动点“从断点继续”才授权重新绑定。

## 验证

全套276项通过（100.82秒），启用原生与无头浏览器开关。新测试覆盖：SSL只初始化一次、三个池只创建一次、Cookie隔离、共享起始节流、任意单账号可用、弹幕第2段失效后从同段接管、不抢回、不重复存储、旧代数拒写、平台风险不接管、HTTP401权限区别、重复账号拒绝、UP同页接管、退出保留断点、旧游标单次去重降级、备用扫码与退出UI及窄屏无溢出。
真实只读验证使用原主账号：无备用账号亦可请求；两次视频信息请求复用同一会话、SSLContext，实际间隔配置0.75秒。未导入实验账号，也未改写原登录态。
实验阶段曾验证公开评论/楼中楼/弹幕/UP断点跨账号可使用，但自然到期、私有内容、不同网络和长时间运行仍需用户验收。一次失效接管自动测试不等于覆盖所有平台分页行为。
